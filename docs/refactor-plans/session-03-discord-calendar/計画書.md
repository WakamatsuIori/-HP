## 1. 現状理解（実行者への文脈共有)

オーナー（非エンジニア）が Discord のスラッシュコマンドで自分のGoogleカレンダーを操作し、HPの再ビルドやポスター生成も発火できる仕組み。**Cloudflare Pages Functions** 上で動く（`functions/` ディレクトリが Pages に自動同梱される）。

- `functions/discord/interactions.ts`（373行・中核）— 全コマンドの受け口 `onRequestPost`:
  1. **署名検証**（Ed25519、`JSON.parse` より**前**、失敗401）: 106-113行
  2. PING→PONG: 118-120行
  3. **認可 `isOwner`**（許可リスト空なら全員拒否 = fail-closed）: 90-98, 127, 190行
  4. コマンド分岐:
     - `/予定`（129-163行）— 月/日/時刻/タイトルの選択値から**確認カード**（embed＋確定/やり直しボタン）を外部通信なしで同期返却。確定データはボタンの `custom_id`（`encodePendingId`）と embed.title に載せて往復する＝**KV不要方式**
     - `/予定表`（165-170行）→ `ctx.waitUntil(handlePoster)` + DEFERRED応答
     - `/予定消去`（172-178行）→ 日付必須・`ctx.waitUntil(handleDelete)` + DEFERRED
     - `/更新`（180-183行）→ `ctx.waitUntil(handleRebuild)` + DEFERRED
  5. ボタン押下（MESSAGE_COMPONENT、188-222行）— 認可再チェック→キャンセル or 確定。確定時は waitUntil 登録後**即座に UPDATE_MESSAGE でボタンを除去**（二重登録の実用的防止）
  6. waitUntil 内: `handleConfirm`（228-273行、KVがあれば1日30件ガード→カレンダー insert）／`handleDelete`（284-313行）／`handlePoster`・`handleRebuild`（316-373行、GitHub `repository_dispatch` 発火）
- `functions/_lib/discord.ts`（82行）— Ed25519署名検証・Interaction定数・レスポンス/ボタン/Embedビルダー。
- `functions/_lib/google.ts`（166行）— サービスアカウントJWT自前署名→アクセストークン、Calendar insert/list/delete、Sheets追記（**問い合わせフォーム=session-04 と共用**）。
- `functions/_lib/datetime.ts`（187行）— JST固定の日時純ロジック＋確認カードの `encode/decodePendingId`。テスト27件で厚く固定済み。
- `scripts/register-discord-commands.mjs` — コマンド定義をDiscordへPUT登録する単発スクリプト（Actions の `register-commands.yml` から実行）。

### 絶対に壊してはいけない挙動（Behaviors To Preserve 該当分）

1. **署名検証が `JSON.parse` より前・失敗401**（`interactions.ts:106-115`）。順序を変えない。
2. **PING→PONG**（118-120行）。Discordのエンドポイント検証に必須。
3. **3秒以内応答**: `/予定表`・`/予定消去`・`/更新` は waitUntil＋DEFERRED。`/予定` と確定ボタンは**外部通信なしの同期即答**。リファクタで同期パスに `await fetch` を挟まない。
4. **カレンダー書き込みは insert のみ**。update/PATCH を追加しない（一方向・追記の原則）。
5. **deleteEvent の 404/410 は成功扱い**（`google.ts:137-144`、冪等性）。
6. **FEATURED_MARK `'#おすすめ'`** は `src/lib/featured.ts` の定義を import（値を変えない・featured.ts に依存を足さない）。
7. **repository_dispatch のイベント名** `make-poster`（`poster.yml` と契約）・`rebuild-site`（`build.yml` と契約）、`client_payload.week` の値 `'今週'|'来週'`。
8. **custom_id 形式** `yt:c|…`（確定）/`yt:x`（キャンセル）と「タイトルは embed.title 経由」の往復契約。**Discord上に表示中の確認カードが残っている可能性がある**ため、この形式を変えない。custom_id は100字以内（テストで固定済み）。
9. fail-closed 認可（`DISCORD_ALLOWED_USER_IDS` 空＝全員拒否）を緩めない。

### 検証の制約

- `functions/` は `astro build` の型チェック対象外・`npm test` も型検査はしない。ただし **`onRequestPost` は Node 24 でそのまま呼べる**（Request/Response/crypto.subtle がグローバルにある）ため、vitest での統合テストが最も再現性の高い検証手段。
- Discord経由のE2E（実コマンド実行）は本番でしかできない。**このセッションでは本番E2Eを行わない**（マージ後にオーナーが手動確認する。手順は §6 の報告に含める）。
