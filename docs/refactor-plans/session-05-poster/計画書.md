## 1. 現状理解（実行者への文脈共有）

毎週日曜18:00 JST に GitHub Actions が週間予定のポスター画像（1920×1080 PNG）を生成し、Discord に投稿する仕組み。Discord の `/予定表` コマンドからも随時起動できる。

```
[トリガー] .github/workflows/poster.yml
  ├─ schedule: '0 9 * * 0'（日曜09:00 UTC=18:00 JST）→ 来週分
  ├─ workflow_dispatch: 週を「今週/来週」で選択
  └─ repository_dispatch types:[make-poster] ← Discord /予定表（client_payload.week が '今週'|'来週'）
[本体] node scripts/make-poster.mjs（Node 24 の型ストリッピングで src/lib の .ts を直接 import）
  (1) ics取得: 素の fetch（36行）— 窓 [now-24h, now+21日]（38-39行）
  (2) パース: src/lib/ics.ts の parseIcsEvents を再利用
  (3) 週データ: src/lib/weekly.ts の buildWeek を再利用
  (4) HTML差し込み: scripts/poster/inject.mjs — テンプレ内の
      `const WEEK = {...};` と `const schedule = [...];` を正規表現でJSON置換
  (5) 撮影: ubuntu-latest にプリインストールの google-chrome を --headless=new で起動し --screenshot
  (6) sharp で 1920×1080 に整形
  (7) Discord Webhook（DISCORD_POSTER_WEBHOOK_URL、無ければ DISCORD_WEBHOOK_URL）へ multipart 投稿。
      両方未設定なら画像生成のみでスキップ
[失敗通知] poster.yml 66-75行 — job 失敗時に DISCORD_WEBHOOK_URL へ curl（未設定なら無音）
```

- `scripts/poster/template.html`（270行）— ポスターの見た目。単体でブラウザで開くとサンプルデータでプレビューできる。**描画側JSが `esc()` で全フィールドをエスケープしてから innerHTML に入れる**（§3対応済み・251-268行）。193行に立ち絵の巨大base64（約2.4MB）が埋まっている。
- `tests/poster-inject.test.ts`（5件）— 差し込みの置換・特殊文字・`$&` 等の置換特殊シーケンス耐性を固定。ただし**模擬テンプレ**を使っており、実 template.html の形とは突き合わせていない。

### 絶対に壊してはいけない挙動

1. cron `'0 9 * * 0'` と `concurrency: group: weekly-poster / cancel-in-progress: false`（`poster.yml:9-10, 22-24`）。
2. `repository_dispatch` のイベント名 `make-poster` と `client_payload.week`（`'今週'|'来週'` の日本語リテラル）— `functions/discord/interactions.ts` 側との契約。
3. テンプレ側 `esc()` によるエスケープ（外部入力＝カレンダー予定タイトルの無害化）。
4. Webhook 未設定なら投稿スキップ（画像生成のみ）の分岐。
5. `src/lib/weekly.ts` 等の**拡張子付き import**（Node 直接実行の前提）。
6. `WeekData`/`WeekDay` のフィールド名（`ja/date/time/title/featured/month/range`）— テンプレ差し込みとの契約。

### ローカル検証の道具（安全・実投稿なし）

- デモカレンダー: `node tests/demo-ics-server.mjs` → `http://127.0.0.1:8125/demo.ics`
- dry-run: Webhook 環境変数が無ければ投稿は自動スキップされる。**シェル環境や `.env` に `DISCORD_WEBHOOK_URL` 等が残っていると実投稿されるため、必ず `env -u` で伏せて実行**:

  ```bash
  env -u DISCORD_WEBHOOK_URL -u DISCORD_POSTER_WEBHOOK_URL \
    ICS_URL=http://127.0.0.1:8125/demo.ics POSTER_WEEK_OFFSET=0 \
    CHROME_BIN=$(command -v google-chrome || command -v chromium || command -v chromium-browser) \
    node scripts/make-poster.mjs
  ```

  期待: 「画像を生成しました: …/weekly_schedule.png」→「（Webhook未設定のため投稿はスキップ。画像のみ生成）」。Chrome が無い環境では (5) で失敗する — その場合は差し込みまでの検証（S5-01 のテスト＋ §3 の手動確認）で代替し、撮影系はCIに委ねる。

### S5-02: 差し込み失敗を「無言の素通し」から「即エラー」に変える

- **対象**: `scripts/poster/inject.mjs:15-20`
- **問題**: `String.replace` は**パターン不一致なら元文字列をそのまま返す**。テンプレを編集して形が変われば（手順書は「見た目はtemplate.htmlで調整できます」と編集を推奨している）、差し込み失敗を誰も検知できず、**サンプルデータ「雑談配信…」のポスターが本番Discordへ正常投稿される**。`CLAUDE.md` §4「中途半端なデータで成功させない」に反する。
- **どう変えるか**: 各置換の成立を確認し、不成立なら throw:

  ```js
  export function injectPosterData(tpl, data, fitStyle) {
    let weekHit = 0;
    let scheduleHit = 0;
    let headHit = 0;
    const out = tpl
      .replace(/const WEEK = \{[^}]*\};/, () => { weekHit++; return `const WEEK = ${jsonForScript({ month: data.month, range: data.range })};`; })
      .replace(/const schedule = \[[\s\S]*?\];/, () => { scheduleHit++; return `const schedule = ${jsonForScript(data.schedule)};`; })
      .replace('</head>', () => { headHit++; return fitStyle; });
    if (weekHit !== 1 || scheduleHit !== 1 || headHit !== 1) {
      throw new Error(
        `テンプレートへの差し込みに失敗しました（WEEK:${weekHit} schedule:${scheduleHit} head:${headHit}）。scripts/poster/template.html のプレースホルダを確認してください。`,
      );
    }
    return out;
  }
  ```

  ※現行実装の置換関数・JSON化ヘルパの名前は `inject.mjs:5-20` の現物を保つ（上はスケッチ。`$&` 対策の「置換値を関数で返す」形を**必ず維持**する）。あわせてテストを追加:

  ```ts
  it('プレースホルダが無いHTMLには差し込めず例外を投げる（無言の素通し禁止）', () => {
    expect(() => injectPosterData('<html><head></head><body></body></html>', data, '</head>')).toThrow(/差し込みに失敗/);
  });
  ```

  throw により make-poster.mjs が異常終了 → Actions が失敗 → 失敗通知が飛ぶ、という**安全側の連鎖**になる。
- **完了条件**: `npx vitest run tests/poster-inject.test.ts` → 全パス（既存5件＋S5-01＋本項目分）。既存5件の期待値は**変更不要のはず**（正常系は置換1回ずつ成立するため）。
- **リスクと戻し方**: 「失敗を成功にしない」方向のみの変更。万一テンプレの現物がプレースホルダ2個以上マッチ等でエラーになったら、それは実バグの発見なので中断して報告。`git revert`。
- **依存**: S5-01

### S5-03: ics取得を fetchText 再利用にし、HTTPエラーの静かな失敗を塞ぐ

- **対象**: `scripts/make-poster.mjs:36` と import 部（19-21行）
- **問題**:

  ```js
  const icsText = await (await fetch(ICS_URL)).text();
  ```

  `res.ok` チェックが無いため、HTTPエラー（404/500やGoogleの一時エラーページ）でも `.text()` は成功し、node-ical が0件を返して**「全日お休み」のポスターが正常投稿される**（Actionsも成功扱い＝失敗通知も飛ばない）。§4「中途半端なデータで成功させない」「故障の自己通知」の両方に反する。タイムアウトも無い。
- **どう変えるか**: サイト本体と同じ fetch層を再利用（`src/lib/fetcher.ts` は import ゼロの純ファイルなので Node 直接実行で安全に読める）＋ ics らしさの軽いガード:

  ```js
  import { fetchText } from '../src/lib/fetcher.ts';
  // ...
  const icsText = await fetchText(ICS_URL);   // ok チェック＋15秒タイムアウト付き
  if (!icsText.includes('BEGIN:VCALENDAR')) {
    throw new Error('取得した内容が .ics 形式ではありません（カレンダーURLの応答異常）。');
  }
  ```

  ※session-01 の S1-04 適用後、fetchText のエラー文は「URLのオリジンのみ」になっており、Secrets の ICS_URL 全文がログに出ない点でも整合する。
- **完了条件**: §1 の dry-run（デモicsサーバー使用）が従来どおり成功しPNGが生成される。さらに異常系の確認として、デモサーバーを**起動せずに**同コマンドを実行し、プロセスが**非0終了**すること（fetch失敗で throw）。`npm test` 全パス。
- **リスクと戻し方**: 取得成功パスは挙動不変。新たに効く15秒タイムアウトはCI上で妥当。`git revert`。
- **依存**: S5-00（dry-run 手順）。※Chrome が無い環境では「PNG生成まで」の確認を「`make-poster.mjs` が (4) 差し込みログまで進み、Chrome起動で失敗する」ことの確認で代替してよい（fetch部の検証としては十分）。

### S5-04: 取得窓をHP側と揃える（「今週」ポスターの消化済み日が休業に化けるバグ）

- **対象**: `scripts/make-poster.mjs:38-39`
- **問題**:

  ```js
  const winStart = new Date(now.getTime() - 24 * 3600 * 1000);        // 過去24時間
  const winEnd = new Date(now.getTime() + 21 * 24 * 3600 * 1000);     // 21日先
  ```

  HP側の週間データは同じ問題を「窓 [-8日, +16日]」で解決済み（`src/lib/loadSchedule.ts:49-55` のコメント「過ぎた日の予定もボードに残る（消化済みが『休業』に化けない）」）。ポスターは `-24h` のままなので、**土曜に `/予定表 今週` を打つと月〜金の実施済み配信が「お休み」表示になる**。日曜の自動実行（来週分）では顕在化しないため気づかれていない。
- **どう変えるか**: HP側と同じ窓に合わせる:

  ```js
  // HP側の週間ボード窓（src/lib/loadSchedule.ts の loadWeekEventsWith）と同じ値。
  // 過去8日〜先16日: 「今週」を選んでも消化済みの日が「お休み」に化けない。

  const winEnd = new Date(now.getTime() + 16 * 24 * 3600 * 1000);
  ```

  （`buildWeek` は週内の日付キーでしか予定を拾わないため、窓が広がっても出力は「化けていた休業が正しく埋まる」方向にしか変わらない）
- **完了条件**: dry-run（`POSTER_WEEK_OFFSET=0`＝今週）で、デモics内の**今週すでに過ぎた日の予定**がポスターに載ること（`tests/fixtures/demo.ics` の内容と照合。過去日の予定が無ければ demo.ics 側でなく一時的にローカルコピーへ過去日イベントを足した ics で確認してよい — fixtures は変更しない）。`npm test` 全パス。

### S5-05: 失敗通知のフォールバックと curl の失敗検知

- **対象**: `.github/workflows/poster.yml:66-75`
- **問題**: 失敗通知が `DISCORD_WEBHOOK_URL` **のみ**に依存し、未設定構成では失敗が無音になる（手順書 `docs/setup/08-poster.md` が必須として案内するのは `DISCORD_POSTER_WEBHOOK_URL` の方）。また通知 curl に `-f` が無く、通知自体の失敗も無音。
- **どう変えるか**: 通知先を本体（`make-poster.mjs:26`）と対称のフォールバックにし、curl を `-fsS` に:

  ```yaml
  env:
    NOTIFY_URL: ${{ secrets.DISCORD_WEBHOOK_URL != '' && secrets.DISCORD_WEBHOOK_URL || secrets.DISCORD_POSTER_WEBHOOK_URL }}
  run: |
    if [ -n "$NOTIFY_URL" ]; then
      curl -fsS -H 'content-type: application/json' -d "$PAYLOAD" "$NOTIFY_URL"
    fi
  ```

  ※既存ステップの構造・PAYLOAD の組み立ては 66-75 行の現物を維持し、URL 決定部分と `-fsS` だけを変える。GitHub Actions の式で上記の三項が書けない場合はシェル側で `NOTIFY_URL="${DISCORD_WEBHOOK_URL:-$DISCORD_POSTER_WEBHOOK_URL}"` とする（両Secretsを env で渡す）。
- **完了条件**: YAML構文の確認（`npx --yes yaml-lint .github/workflows/poster.yml` があれば使用、無ければ目視＋インデント確認）。マージ後、オーナーに workflow_dispatch（今週）で1回実行してもらい成功を確認。
- **リスクと戻し方**: 現在は `DISCORD_WEBHOOK_URL` が設定済みのため通知先は実質変わらない（フォールバックは保険）。異常時 `git revert`。**エラー通知がポスター用チャンネルに流れうる構成変更である旨を完了報告に明記**し、オーナーの認識を得る。
- **依存**: S5-00
