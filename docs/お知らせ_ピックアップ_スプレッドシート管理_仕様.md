# サイト管理シート（お知らせ／ピックアップ／FAQ／グッズ を Googleスプレッドシートで管理）仕様

> 母艦＝設計のみ。**実装は vtuber-hp（メイン）**：プランモード→承認→実装→/code-review→停止。
> 本人決定（2026-06-22）：**Discordコマンドで投稿する案（B3/B4）は採用しない**。代わりに**1枚のスプレッドシート（複数タブ＝サイト管理パネル）で管理**し、サイトは**ビルド時に読むだけ**。反映は既存の**毎時ビルド**＋**Discord `/更新`（今すぐ反映ボタン）**。読み取りは**サービスアカウントで非公開読み**。
> **管理タブ＝“メニュー”（サイトごとに要るものだけ有効化＝汎用ツール化の利点）**：①お知らせ ②ピックアップ ③**ファンアート（ファンが描いてくれたイラストのギャラリー）** ④**グッズ／リンク（`goods.astro` の手動運用を置換）** ⑤**FAQ（よくある質問・任意。使う人だけ有効化）**。読み機構 `loadSheet.ts` は一度作れば各タブの追加/省略は安い。「よく増える/変わる・表で表せる」ものだけ載せる（プロフィール/SNSリンク/キャッチコピー＝めったに変わらない→コードのまま）。
> ※ 和香松庵本人サイトで③〜⑤のどれを実際に出すかは本人選択。FAQは「人によっては入れる」前提で**部品として用意**する。
> 関連：[自動化_実装手順_runbook](自動化_実装手順_runbook.md)／[鮮度フォールバック04](../../HP制作支援/制作工程/04-鮮度レイヤー_フォールバックUI仕様.md)／既存 `src/lib/loadSchedule.ts`（カレンダー→ビルド時読込の前例）。

## 0. なぜこの形か（要点）
- **既存と同じ仕組み**：配信予定は「Googleカレンダー → ビルド時読込 → 反映」で稼働中。お知らせ/ピックアップも「Googleスプレッドシート → ビルド時読込 → 反映」＝**同じ一方向の読み取り**。
- **一番やっかいな所が消える**：Discordからリポジトリのコードを書き換える必要なし（＝書込権限トークン不要・サイトを壊すリスクなし）。サイトは表を**読むだけ**。
- **編集がラク**：表で一覧・並べ替え・下書き・履歴。スマホ/PCどちらでも。
- **「更新の実行」はDiscordのまま**：`/更新` コマンドは既に存在（`functions/discord/interactions.ts` → repository_dispatch `rebuild-site`）。これを**今すぐ反映ボタン**として流用。新コマンドは作らない。

## 1. スプレッドシートの構造（1ファイル・2タブ）

オーナー（和香松庵）が1枚作成 → **サービスアカウントのメールアドレスに「閲覧者」で共有**。タブ名はコードで参照するので固定する。

### タブ①『お知らせ』（→ `src/config/information.ts` の `InfoItem[]` に対応）
| 列 | ヘッダ | 必須 | 内容 | 既存フィールド |
|---|---|---|---|---|
| A | 日付 | ✓ | 例 `2026.06.22`（表示そのまま） | `date` |
| B | カテゴリ | ✓ | `info`/`goods`/`stream`/`song`/`costume` 等の自由ラベル | `category` |
| C | タイトル | ✓ | 本文の見出し | `title` |
| D | リンク | – | 外部URL or サイト内パス（`/schedule` 等）。空＝リンク無し | `url?` |
| E | 画像 | – | バナーURL or `public/`配下パス。**空＝金×黒の既定デザイン**（実装済） | `image?` |
| F | 公開 | – | `TRUE`/`FALSE`。`FALSE`は下書き＝サイトに出さない | （新・フィルタ用） |

- **並び順**：上の行＝新しい順（表示もこの順）。実装側は「F=TRUE の行だけ」「A〜Cが空の行はスキップ」。
- 先頭行はヘッダ固定。2行目以降がデータ。

### タブ②『ピックアップ』（→ `src/config/featured.ts` に対応）
| 列 | ヘッダ | 必須 | 内容 | 既存 |
|---|---|---|---|---|
| A | 動画URLまたはID | ✓ | YouTubeの `watch?v=○○` / `/shorts/○○` / 生ID。実装側で**IDを抽出** | `featuredVideoIds[]` |
| B | ラベル | – | おすすめ吹き出し（例「はじめましての方はこちら！」） | `featuredLabels[]` |
| C | 表示 | – | `TRUE`/`FALSE`。FALSEは出さない | （新・フィルタ用） |

- **行＝表示順**（上から）。上限3本（既存仕様）。0行/全FALSE＝既存どおり「最新動画の上位3本」に自動フォールバック。
- ⚠️ 注意：これは**動画セクションのPICK UP**。週間ボードの強調（`FEATURED_MARK='#おすすめ'`／`src/lib/featured.ts`）とは別物。混同しない。

### タブ③『ファンアート』（新設＝ファンが描いてくれたイラストのギャラリー）
| 列 | ヘッダ | 必須 | 内容 |
|---|---|---|---|
| A | 画像 | ✓ | **Driveの画像ファイル名**（例 `fanart_001.png`／§画像参照）。or `public/`パス・外部URL |
| B | 作者名 | ✓ | 描いてくれた人の名前（**出典明記＝必須**） |
| C | 作者リンク | ✓ | 作者のX/pixiv等URL（クレジット＝必須。タップで作者へ飛ぶ） |
| D | コメント | – | ひとこと添え書き（任意） |
| E | 掲載許可 | – | `TRUE`＝本人が許可確認済み（自己管理用の目印）。**許可済みだけ載せる** |
| F | 公開 | – | `TRUE`/`FALSE`。FALSEは下書き |

- 表示：新規 `src/pages/fanart.astro`（グリッドのギャラリー）。各作品に**作者名＋作者リンクを必ず併記**。
- ⚠️ **権利・マナー**：ファンアートの著作権は作者にある。**①許可を得たもの ②必ずクレジット（作者名＋リンク） ③作者が削除依頼したら下げる**、を運用前提に。シートのE列「掲載許可」で本人が管理。
- 画像は **Googleドライブのフォルダにドロップ→ビルド時に取り込み**（§画像の入れ方）。Driveの直リンクは使わない。

### タブ④『グッズ』（`goods.astro` の手動運用を置換。BOOTH RSS終了対策）
| 列 | ヘッダ | 必須 | 内容 |
|---|---|---|---|
| A | 商品名 | ✓ | タイトル |
| B | リンク | ✓ | BOOTH等の商品URL |
| C | 価格 | – | 例 `¥1,200`（空可） |
| D | 画像 | – | 商品画像URL or `public/`パス。空＝既定デザイン |
| E | 種別 | – | デジタル/物理/ボイス 等（任意ラベル） |
| F | 状態 | – | `販売中`/`SOLD`/`準備中`（出し分け） |
| G | 公開 | – | `TRUE`/`FALSE` |

- 行＝表示順（上から）。`goods.astro` をこのタブ駆動に差し替え（現状＝リンク手動）。0行/全FALSEは「準備中」表示 or 非表示。

### タブ⑤『FAQ』（よくある質問・任意＝使う人だけ有効化。汎用部品として用意）
| 列 | ヘッダ | 必須 | 内容 |
|---|---|---|---|
| A | 質問 | ✓ | Q（見出し） |
| B | 回答 | ✓ | A（本文・改行可） |
| C | カテゴリ | – | 配信/グッズ/コラボ 等（任意・絞り込みや並びに） |
| D | 公開 | – | `TRUE`/`FALSE`。FALSEは下書き |

- 表示：`src/pages/faq.astro`（or トップ/aboutに節を追加）。アコーディオン等は任意。**このタブが空ならFAQセクション自体を出さない**（有効化は中身を入れるだけ）。
- **運用ループ（使う場合）**：マシュマロで来た質問のうち良いものをFAQタブに転記→反映（受け口＝マシュマロ、掲載＝FAQシート）。
- 本人サイトで使うかは任意。**クライアント（汎用LP）では入れる人が多い想定**なので部品として実装しておく。

## 1.5 画像の入れ方（Googleドライブ → ビルド時取り込み）

本人決定（2026-06-22）：画像も**Googleの中で完結**させる。シートに文字、画像はDriveフォルダにドロップ。

- ❌ **Drive直リンクはしない**（`uc?export=view` 等）：Googleが直リンクを嫌い、リダイレクト/制限/スキャン画面で**不安定**。訪問者のブラウザがDriveを読む形は採らない。
- ✅ **ビルド時に取り込む**：サイト組み立て時に**シートと同じサービスアカウントでDrive APIから画像を1回ダウンロード→`public/`に焼き込む**。訪問者は普通の静的画像をCloudflareから受け取る＝高速・安定。Driveが落ちても表示は無事。

**運用（オーナー）**：Driveの所定フォルダ（例『ファンアート画像』）に画像をドロップ→シートの画像列に**ファイル名**を書く。GitHubもPCも不要。

**実装メモ（メイン）**：
- Driveの画像フォルダを**SAメールに「閲覧者」共有**＋スコープ `https://www.googleapis.com/auth/drive.readonly` 追加（既存SA鍵を流用。`getAccessToken` の scope を用途別に）。
- ビルド時：`files.list`（`'<folderId>' in parents`）でフォルダ内一覧→各 `files.get?alt=media` でダウンロード→`public/_assets/`等へ。シートの「ファイル名」と突き合わせ。
- **速度**：Drive metadata の `modifiedTime`/`md5Checksum` で**変わった画像だけ再取得**（毎ビルド全DLしない）。`sharp`（導入済）でリサイズ/圧縮可。
- **フォールバック**：取得失敗時は**前回取り込んだ画像で継続**（ビルド止めない／白画面なし＝[鮮度04]）。スナップショットはコミット対象にしてもよい。
- 必要env：`DRIVE_IMAGE_FOLDER_ID`（画像フォルダID）。`GOOGLE_SA_*` は流用、ビルド読込なので**GitHub Secretsにも要ミラー**（シート読込と同条件）。
- 対象：ファンアート（必須級）・お知らせバナー・グッズ画像。**画像列が空なら既定デザイン**（金×黒／実装済）でOK＝凝らない時はDrive不要。

## 2. 仕組み（データの流れ）
```
オーナー: スプレッドシートを編集（行を足す/直す/公開チェック）
   ↓ （①自動）
毎時ビルド（既存 build.yml schedule）→ シートを読み直す → 反映（最大1時間）
   ↓ （②今すぐ）
Discordで /更新 → repository_dispatch(rebuild-site) → 数分で反映
   ↓
サイト: ビルド時にシートをサービスアカウントで読む → お知らせカード／PICK UP に反映
```
取得**失敗時は前回値（=`src/config/*.ts` の静的内容）で表示継続**。サイトは白くならない（[鮮度04]の思想）。

## 3. 実装メモ（メインセッション向け・触る所）

### 3-1. 認証の置き場所（ここが今回の肝）
- 既存 `functions/_lib/google.ts` の `getAccessToken` は **scope が `calendar.events` 固定**＋**エッジ関数専用**。お知らせ読込は**ビルド時（Node）**なので、**ビルド時用のSAトークン取得**が要る。
- 方針：`getAccessToken` を **scope引数つきに一般化**（デフォルトは現状維持で後方互換）。ビルド時から使える形に。Node24は `globalThis.crypto.subtle` 利用可（WebCryptoそのまま動く）。
- 必要scope：`https://www.googleapis.com/auth/spreadsheets.readonly`。

### 3-2. 新規/改修ファイル
| ファイル | 役割 |
|---|---|
| `src/lib/loadSheet.ts`（新） | SAトークン取得→ `GET https://sheets.googleapis.com/v4/spreadsheets/{SHEET_ID}/values/{タブ名}!A:F` → 2次元配列を返す。`fetcher.ts`流用・timeout・失敗throw |
| `src/lib/loadInformation.ts`（新） | 『お知らせ』タブ→ `InfoItem[]`（F=TRUEのみ・必須欠落行スキップ）。失敗時 `information.ts` の静的配列にフォールバック |

### 3-3. 環境変数・初期設定（クリック手順の骨子）
- Google Cloud の該当プロジェクトで **Google Sheets API を有効化**。
- スプレッドシートを**SAのメール（`GOOGLE_SA_EMAIL`）に「閲覧者」で共有**。
- **GitHub Actions（build.yml）に Secrets を追加**：`GOOGLE_SA_EMAIL`／`GOOGLE_SA_PRIVATE_KEY`（※今はCloudflare Pages側にしか無い→ビルドでも読むので**GitHubにもミラー**）／`INFO_SHEET_ID`（スプレッドシートID＝URLの `/d/○○/` 部分）。
- `.env`（ローカル）にも同名で置けばローカルビルド確認可。**秘匿＝コード/リポジトリに書かない**。

### 3-4. フォールバック / 受け入れ条件
- [ ] シート正常 → お知らせ/PICK UP がシートどおり反映
- [ ] F列/C列が `FALSE` の行は出ない（下書きが漏れない）
- [ ] 取得失敗（鍵ミス/ネット遮断/API無効）→ **`config/*.ts` の静的内容で表示継続・ビルド止まらない・白画面なし**
- [ ] 『ピックアップ』0行/全FALSE → 既存の「最新3本自動」に戻る
- [ ] 必須列（日付/カテゴリ/タイトル）が空の行はスキップ（崩れない）
- [ ] `/更新` 実行 → 数分で反映／何もしなくても毎時で反映
- [ ] D1（失敗通知）を入れる場合：シート取得失敗時に `DISCORD_WEBHOOK_OPS` へ1通（スパムにしない）

## 6. 受け取り系（お便り／お仕事依頼）とスパム対策
本人懸念（2026-06-22）：**「独自フォームは嵐（スパム）対策できんよな」**。整理：

- **C1 お便り → 廃案（マシュマロに一本化）**。`site.ts` に既にマシュマロのリンクあり。マシュマロは**匿名投稿のスパム/通報対策を運営側が持つ**ので、自前フォームより安全。受け口＝マシュマロに集約。
- **C2 お仕事依頼 → 案A（自前フォーム＋Turnstile）で確定**（本人決定 2026-06-22）。マシュマロは商談に不向き。Turnstile＋honeypotで機械スパムはほぼ止まる（依頼は連絡先必須で荒れにくい）。見た目をサイトに統一できる。

### 6-1. C2の構成（フォーム → 通知＋記録の二段構え）
本人方針：**「できたらDiscord通知」「詳細はどこかに残す」**＝取りこぼし防止のため通知と記録を分ける。
```
依頼フォーム送信（work.astro）
   ↓ functions/api/contact.ts（honeypot→Turnstile siteverify→検証）
   ├─→ ① Discord通知：すぐ気づく用・要点だけ（DISCORD_WEBHOOK_FORM）
   └─→ ② スプレッドシートに1行追記：記録用・全文＋連絡先＋日時（＋対応状況メモ列）
```
- **① Discord**：埋め込みで「新しいお仕事依頼／種別／お名前／要点」を短く。流れて消えても②に残る。
- **② シート追記**：Sheets API `spreadsheets.values.append` で『お問い合わせ』に1行。本人は表で一覧・`対応状況`列で管理（未対応/対応中/完了）。
- **取りこぼし防止**：①と②は**独立に試行**し、片方失敗でももう片方は実行（両方失敗時のみエラー応答＋ログ）。依頼を落とさない。

### 6-2. 設計上の注意（最小権限）
- 記録先シートは**コンテンツ管理シートと分ける**のが安全。理由：コンテンツ用シートはSAが**閲覧（読み取り）**だけで足りるが、お問い合わせ記録は**書き込み（編集）**が要る。同居させるとSAにサイト全コンテンツの編集権を与えることになる。
  - → **お問い合わせ専用シート（SA=編集者）** ＋ **コンテンツ管理シート（SA=閲覧者）** の2ファイル構成。`getAccessToken` の scope は用途別（読み=`spreadsheets.readonly`／書き=`spreadsheets`）。
- プライバシー：フォームに「内容は運営（和香松庵）が対応のため保管します」と明記。記録シートは**非公開**（共有しない）。連絡先など個人情報を含むため取り扱い注意。
- 環境変数（追加）：`INQUIRY_SHEET_ID`（記録先）。既存 `GOOGLE_SA_*`（Pages）を流用、`DISCORD_WEBHOOK_FORM`／`TURNSTILE_SITEKEY`・`TURNSTILE_SECRET`。
- 受け入れ：正常送信でDiscord着弾＆シートに1行／honeypot埋めで破棄／Turnstile不合格で弾く／Discord失敗でもシートには残る（逆も可）／必須空・長文でエラー。
